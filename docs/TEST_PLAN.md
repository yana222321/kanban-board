# План тестирования

## 1. Цели

- Подтвердить корректность функциональных требований Kanban-доски.
- Обеспечить регрессионную защиту ключевых сценариев (аутентификация, проекты, доски, карточки, права доступа).
- Оценить производительность и устойчивость API под нагрузкой.
- Выявить уязвимости зависимостей и типовые веб-уязвимости.

## 2. Объект тестирования

- REST API backend (Express + Prisma + PostgreSQL).
- SPA frontend (React).
- Интеграция frontend ↔ backend (прокси `/api`).

## 3. Уровни и виды тестирования

| Уровень                  | Инструмент           | Что проверяет                                            |
| ------------------------ | -------------------- | -------------------------------------------------------- |
| Модульное                | Jest                 | Утилиты (JWT, пароли), бизнес-правила (права доступа), обработка ошибок |
| Интеграционное           | Jest + Supertest     | HTTP-эндпоинты, валидация, БД, авторизация               |
| E2E                      | Playwright           | Пользовательские сценарии через браузер                  |
| Нагрузочное              | k6                   | Пропускная способность и задержки API                    |
| Безопасность (SCA)       | npm audit            | Уязвимости зависимостей                                  |
| Безопасность (DAST)      | OWASP ZAP baseline   | Типовые веб-уязвимости                                   |
| Статический анализ       | ESLint, tsc          | Качество и типы кода                                     |

## 4. Тестовое окружение

- Node.js 22, npm.
- PostgreSQL — отдельная БД `kanban_test` для интеграционных тестов (изоляция от dev-данных).
- Браузер Chromium (Playwright), headless.
- CI: GitHub Actions, ubuntu-latest, сервис-контейнер `postgres:16`.

## 5. Изоляция и данные

- Интеграционные тесты выполняются в БД `kanban_test`; перед прогоном глобальный setup применяет миграции (`prisma migrate deploy`).
- Перед каждым тестом таблицы очищаются; тестовые данные создаются фабриками (`tests/helpers/factories.ts`).
- E2E использует dev-БД с seed-данными; создаваемые сущности уникальны (по timestamp), что позволяет повторные прогоны.
- По завершении прогона E2E тестовые сущности удаляются автоматически (Playwright `globalTeardown` → `backend` скрипт `cleanup:e2e`), поэтому dev-БД не засоряется.

## 6. Критерии входа

- Код собирается (`npm run build`), линт и типы без ошибок.
- Развёрнута целевая БД, применены миграции.

## 7. Критерии выхода

- Все тесты зелёные (backend unit/integration, E2E).
- Покрытие не ниже порогов: строки ≥ 80 %, ветви ≥ 70 %.
- Нагрузочные пороги k6 выполнены (`http_req_failed < 1 %`, `p(95) < 500 мс`).
- Нет новых уязвимостей уровня high/critical в зависимостях.

## 9. Риски и меры

| Риск                                   | Мера                                                        |
| -------------------------------------- | ----------------------------------------------------------- |
| Загрязнение dev-БД тестами E2E         | Уникальные данные (timestamp), автоочистка после прогона, отдельная БД для интеграции |
| Флаки drag & drop в E2E                | Ожидание закрытия модальных окон перед перетаскиванием      |
| Нестабильность внешних сервисов в CI   | Сервис-контейнеры, фиксированные версии образов             |
| Долгий прогон нагрузочных тестов       | Вынесены в отдельную job по ручному запуску (`workflow_dispatch`) |

## 10. Регулярность

- При каждом push/PR: backend (lint/типы/тесты), frontend (lint/типы/сборка), E2E.
- По требованию: нагрузочное и security-тестирование.
